# M-academy 4.0 — серверная рабочая панель

**Исходный код панели:** [backend/pilot-app/app/overview/page.tsx](backend/pilot-app/app/overview/page.tsx)

**Текущий статус:** новая панель написана в составе **отдельного Next.js-пилота**. Она не опубликована как работающий серверный сайт. GitHub Pages обслуживает только статическую версию 3.2.

## Реализовано в коде

- Проверка сеанса через `supabase.auth.getUser()`.
- Список школ по активным строкам `memberships`, без самостоятельного назначения ролей.
- Выбор школы с ограничением запросов по `school_id`.
- Ролевая сводка классов: `class_teachers` и `class_students` определяют разрешённые классы.
- Учитель: сводка `curriculum_plans`, `lesson_drafts`, `ksp_documents` (только свои материалы), а также доступных заданий.
- Ученик: только свои классы и доступные опубликованные задания (через существующие RLS-политики).
- Администратор: общая сводка доступных классов и заданий, без возможности самоназначения ролей.
- Ссылки на существующие страницы управления классами и заданиями.
- Контрактные проверки на доступ, фильтрацию по школе и отсутствие обращения к ключам ответов.

## Важные ограничения и требования

1. **Код не равен развёрнутому приложению.** Для реальной эксплуатации требуется инфраструктура для Next.js и Supabase.
2. Клиентские фильтры необходимы для интерфейса, но не являются защитой: безопасность держится на **правильных политиках RLS** в базе и доверенном администрировании.
3. Информация ограничена первыми 500 строками на запрос; для больших школ нужна серверная пагинация и уточнение отчётности.
4. Материалы 3.2 в `localStorage` не передаются автоматически на сервер. Нужен контролируемый импорт с привязкой классов и подтверждением учителя.
5. Реальные данные несовершеннолетних не вводить до правовой и технической проверки, тестов разграничения доступа, резервирования и восстановления.
6. Контрактные тесты не заменяют интеграционные тесты RLS на реальной тестовой базе.

## Что настроить для запуска

- Применить миграции [backend/supabase/migrations](backend/supabase/migrations) в изолированном тестовом проекте после проверки безопасности.
- Настроить Supabase Auth, URL перенаправления, тестовые учётные записи взрослых и доверенное назначение ролей.
- Задать **публичные** URL/anon-key в окружении Next.js; **service_role** никогда не размещать в `NEXT_PUBLIC_*`.
- Развернуть `backend/pilot-app` на подходящем хостинге Next.js, не на GitHub Pages.
- Выполнить `npm install`, `npm test`, `npm run lint`, `npm run build`, затем ручные сценарии входа.
- Проверить отдельно: teacher A не видит материалы teacher B, student A не видит student B, школа A не читает школу B.

## Переход локального КТП 3.1 в серверный пилот

В `TeacherMaterials` добавлена загрузка JSON, выгруженного из локального учебного конвейера 3.1. Строки группируются по классу, литере и предмету и показываются как **черновики КТП**. Учитель должен выбрать доступный серверный класс, проверить соответствие предмета, дату, часы и цели обучения, затем отдельно нажать сохранение. Автоматическая миграция данных в сервер или обход RLS отсутствуют.

Ограничения: импорт не переносит локальные задания и не привязывает уроки к строкам КТП автоматически. Учебный год черновика сейчас фиксирован как 2026–2027. Перед эксплуатацией необходимо заменить это настройкой выбранного учебного года. Внешние SQL-миграции также должны быть проверены на целостность и безопасность.
