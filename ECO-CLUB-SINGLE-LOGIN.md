# Единый Google-вход ECO CLUB и M-academy

## Что проверено в исходном коде

ECO CLUB (репозиторий `ecoformat-merke/ecoformat-merke.github.io`) использует Google через **Firebase Authentication** (Firebase-проект `eco-club-40261`), а заявления участников обрабатываются в коллекции Firestore `profiles` со статусами `pending`, `active` и другими.

M-academy использует **Supabase Auth** и отдельную защищённую PostgreSQL с `memberships`, `class_teachers` и `class_students`. Google-вход теперь добавлен через `signInWithOAuth({provider:'google'})`, без какого-либо обращения к приватной Firebase базе.

## Что означает единый вход

- Пользователь может выбрать **тот же Google-аккаунт** на обоих сайтах. Второй пароль не нужен.
- Это **не** означает автоматический общий сеанс: Firebase и Supabase — два самостоятельных поставщика сессий, и Google может снова попросить выбрать учётную запись.
- **Firebase UID и Supabase Auth UID отличаются**. Не используйте Firebase UID как `auth.users.id` в Supabase.
- Подтверждённый email можно использовать только для подготовки администратором списка соответствий, но **не как доказательство школьной роли** и не как основание автоматически переносить оценки или персональные данные.
- Уже существующий профиль ECO CLUB не удаляется и не меняется. Администратор M-academy проверяет текущую роль отдельно.
- Самостоятельное создание учётной записи в Supabase через Google может происходить по настройке OAuth. **Новый аккаунт без записи `memberships` не имеет доступа к школьным данным** благодаря RLS.
- Если участник ранее был приглашён в Supabase по email, нужно отдельно проверить поведение объединения идентичностей и избежать появления второго UID: не предполагайте автоматическое слияние без практического теста.

## Конфигурация после разрешения владельца

1. В тестовом Supabase-проекте настроить Google OAuth Provider и указать Google OAuth Client ID/Secret через защищённую панель Supabase.
2. В Google Cloud Console зарегистрировать OAuth Client, добавить выданный Supabase **callback URL** в список разрешённых redirect URI. Не подставлять адрес ECO CLUB как redirect M-academy. Существующую конфигурацию Firebase ECO CLUB не изменять.
3. Настроить Site URL и список разрешённых redirect URL Supabase на **реальный HTTPS-адрес развёрнутого сервера M-academy**. Код сейчас направляет пользователя обратно на корень этого адреса. GitHub Pages не является сервером Next.js.
4. Выполнить вход под тремя **тестовыми взрослыми** Google-аккаунтами; сравнить идентификатор Supabase Auth UID для каждого с `memberships.user_id`. Роль выдавать только после независимой проверки администратора.
5. Проверить вход, выход, переоткрытие браузера, доступ к другому классу, отсутствие доступа без назначения, ошибку провайдера и отзыв назначения.
6. Для действующего пользователя ECO CLUB с разрешения школы сверить `profiles.status='active'` и роль у администратора, затем **вручную одобрить** соответствующую роль в M-academy. Не копировать всю коллекцию Firestore, фотографии, контакты, пароли, токены или данные школьников.
7. Только после юридического и технического согласования рассматривать ограниченный импорт списка разрешённых пользователей. Анонимный фронтенд и GitHub Pages не должны владеть служебными ключами Firebase или Supabase.

## Политика безопасности

Google доказывает успешную аутентификацию, а не право быть педагогом/администратором. Все разрешения выдаются **через PostgreSQL RLS и администрируемые назначения**, независимо от заявленной роли в ECO CLUB. Файлы браузера не имеют доступа к Supabase service-role key и Firebase Admin SDK.

## Статус

**Готово в исходном коде:** Google OAuth-кнопка, обработка ошибок и сохранение запасного приглашённого email-входа, статические тесты отсутствия самоназначения ролей.

**Не проверено:** реальные Google OAuth Client ID/Secret, URL callback, настройка Supabase в панели, жизненный цикл сессии между двумя отдельными сайтами, объединение ранее приглашённых пользователей и браузерное тестирование. Для них требуется разрешение на внешние настройки в финальном этапе.

## Проверка трёх ролей в интерфейсе M-academy

После разрешённого развёртывания откройте `/auth-check` на HTTPS-домене серверного приложения. Кнопка «Проверить снова» вызывает `auth.getUser()`, выбирает только активные `memberships` текущего Supabase UID и запрашивает разрешённые по RLS школы и классы.

| Тестовый аккаунт | Ожидаемое состояние |
| --- | --- |
| Администратор | Роль `admin`, видны классы только назначенной школы; нет доступа к другим школам |
| Учитель | Роль `teacher`, список назначений `class_teachers`; нет доступа к чужим заданиям и ключам |
| Ученик | Роль `student`, список назначений `class_students`; нет доступа к чужим работам, ключам и оценкам |
| Google-пользователь без `memberships` | «Школьных прав нет»; чтение школьных данных невозможно |

**Не подменяйте проверку:** страница показывает статусы только текущей сессии и не имитирует роли. Чтобы проверить каждую роль, необходимо отдельно войти под соответствующим тестовым аккаунтом. Автоматические PostgreSQL RLS-тесты уже проверяют изоляцию учителя, ученика и неавторизованного участника, однако не тестируют внешнее перенаправление Google.
