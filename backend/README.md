# M-academy: защищённый пилот платформы

**Статус: исходный код пилота. Не развёрнут и не подключён к действующему GitHub Pages.** Публичная версия продолжает работать независимо.

## Что реализовано в коде

- PostgreSQL (ориентир: Supabase) со школами, ролями, классами и назначениями педагогов.
- Политики Row Level Security для разграничения данных по школе, учителю и ученику.
- Раздельное хранение формулировок заданий и закрытых ответов учителя.
- Вход по одноразовой email-ссылке **только для заранее созданных аккаунтов**; пользователь не назначает себе роль.
- Учитель может создать задание и опубликовать его для назначенного класса.
- Ученик из класса видит только опубликованное задание и отправляет ответы транзакционно.
- Учитель видит работы, выставляет баллы и комментарий; ученик видит свою проверенную работу.
- Отдельный список КСП педагога и интерфейс добавления класса администратором.

## Запуск в ИЗОЛИРОВАННОЙ тестовой среде

1. **До развёртывания:** провести юридическую и организационную оценку размещения и обработки данных в Казахстане. Пока использовать только тестовые аккаунты взрослых, вымышленные классы и задания. Не загружать персональные данные учеников.
2. Создать **отдельный** тестовый проект Supabase. Не выполнять миграцию на существующей базе с пользовательскими таблицами: миграция меняет привилегии таблиц схемы \`public\`.
3. Выполнить миграции в таком порядке:
   - \`backend/supabase/migrations/20261123_initial.sql\`
   - \`backend/supabase/migrations/20261123_atomic_submissions.sql\`
4. В Supabase Auth включить email OTP/Magic Link, ограничить допустимые URL редиректа адресом будущего тестового приложения. Создать тестовые аккаунты взрослых доверенным административным способом (например, через защищённый Auth Admin API).
5. Из защищённой административной сессии с правами service role создать запись школы и назначить \`memberships\` для администратора, учителя и тестового «ученика». **Не размещать service role key в браузере, GitHub, публичных переменных среды или клиентском коде.**
6. Добавить класс, назначить \`class_teachers\` и \`class_students\` доверенным способом. Роли в \`memberships\` должны соответствовать назначению.
7. Перейти в \`backend/pilot-app\`, выполнить \`npm install\`, скопировать \`.env.example\` в \`.env.local\` и указать публичный URL и **только** публичный anon/publishable ключ.
8. Выполнить \`npm run dev\`. Открыть \`http://localhost:3000\`. Авторизация и доступ к базе начнут работать **только после** настройки сервера и учётных записей.
9. Запустить \`npm test\` и \`npm run lint\`. После тестового развёртывания провести сценарии ниже.

## Основной сценарий тестирования

- Администратор входит, видит только свою школу и создаёт тестовый класс.
- Учитель без назначенного класса не может создать задание.
- Администратор назначает учителя на класс; учитель публикует три тестовых вопроса и закрытые ключи.
- Тестовый ученик другого класса не видит задания.
- Тестовый ученик назначенного класса видит **только вопросы**, не может читать \`assignment_keys\`, отправляет ответы один раз.
- Повторная отправка отклоняется; случайные вопросы другого задания отклоняются.
- Учитель видит ответы и выставляет результат; ученик видит только свой результат.
- Учитель другой школы не видит задания и результаты.
- Неверифицированный/неназначенный аккаунт не видит данные и не может назначить себе admin.

## Что обязательно проверить до любых реальных данных

- Полное выполнение SQL на отдельном PostgreSQL/Supabase: реальный тест ролей и RLS, не только проверка текста SQL.
- Угрозы: перенос данных между школами, угадывание UUID, попытки повышения привилегий, прямые PostgREST-запросы, повторная отправка, гонки публикации.
- Безопасность email-авторизации, rate limiting, MFA для административных аккаунтов.
- Резервирование, восстановление, журналирование, хранение и удаление данных, пределы загрузок, срок хранения.
- Проверка действующих требований Республики Казахстан по обработке персональных данных детей и месту хранения данных с юридическим специалистом учреждения.
- Полноценные интеграционные тесты на отдельной базе с созданными тестовыми ролями.
- Редактор КТП/КСП и миграцию локальных JSON ещё предстоит подключить к серверной базе.
- Не выставлять оценки за автоматические тренировочные задачи без педагогической проверки.

## Границы текущего результата

Это **подготовленная основа**, а не действующая многопользовательская система. Для запуска необходимы серверный проект, настройка Auth, база, тестовые роли и дальнейшая проверка. Статический сайт GitHub Pages по-прежнему работает локально в браузере без реальной авторизации.

\`npm test\` проверяет **наличие критических ограничений в исходном коде**; это НЕ доказательство фактической безопасности RLS. Реальные RLS-тесты следует провести с подключённой тестовой базой.
