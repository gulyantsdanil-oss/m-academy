## Реальная последовательность запуска

1. Проверить, что тестовая инфраструктура удовлетворяет требованиям хранения данных, доступа к образовательным сведениям и резервирования. Не использовать данные учащихся на этапе пилота.
2. Развернуть независимый тестовый Supabase-проект и применить миграции в установленном порядке.
3. Настроить разрешённый способ входа и redirect URL. Технические аккаунты взрослых тестировщиков создаются по доверенной процедуре.
4. Доверенным административным процессом назначить школе администратора, учителю — класс и предмет, тестовому ученику — соответствующий класс. Не публиковать service-role ключ.
5. Развернуть Next.js из `backend/pilot-app` на сервере, поддерживающем Node.js. GitHub Pages **не** запускает этот backend.
6. Выполнить автоматические проверки: `npm test`, `npm run lint`, `npm run build`.
7. Проверить реальные RLS-сценарии на тестовой базе: запрет доступа между школами, классами и ролями; недоступность ключей ответов ученику; запрет подмены учителя; контроль удаления/редактирования связанных КТП.
8. Проверить сквозной сценарий с фиктивными сведениями: создание класса → КТП → согласование тем → КСП → черновик урока → публикация задания → ответ ученика → оценивание → просмотр результата.
9. Проверить ошибки: параллельное редактирование КТП, повторная отправка работы, неверная тема из чужой школы, ошибка в середине публикации, восстановление после сбоя.
10. Только после успешных проверок и формального разрешения школы рассматривать работу с реальными данными.

## Что НЕ готово и не должно изображаться готовым

- Next.js-пилот **не развернут на публичном сервере**.
- Реальная база, данные школы, Auth и миграции **не подтверждены подключёнными**.
- Новые функции требуют тестирования компиляции/интеграции: исходный код и статические контрактные тесты не равны готовому продукту.
- Удобный полноценный редактор урока с согласованием КСП, интеграция Word/Excel в серверном режиме, массовое назначение пользователей и обширная аналитика ещё требуют разработки и приёмки.
- Нет проверенного регламента резервного копирования/восстановления и проверки нагрузки.

## Архитектурное правило

Публичный статический сайт можно сохранить как витрину и открытые математические материалы. Реальные школьные кабинеты, данные и роли должны работать только через отдельный защищённый сервер и базу с RLS. Нельзя переносить служебные ключи в `index.html`, `v3.html` или JavaScript, доступный анонимным посетителям.
